# The take: record Kari's output to a WAV — 2026-11-03

The first slice of the record button: everything under it. A `kari-recorder` worklet node hangs off the chain's
meeting point (the analyser just before the output, where dry, delayed-dry and pitched paths have already summed),
copies every frame to the main thread, and a streaming 24-bit WAV writer closes the file with cue markers for every
move. No button yet, no storage yet: this slice is reachable from the content script's debug surface only
(`__kari.record.start() / stop() / save(take)`), so nothing a user sees changes. Site-audio export stays local-only
until Jesse's legal ruling; the store listing and `docs/PRIVACY.md` change in the release that ships the button.

## What it does

- **Where it taps.** `AudioController` connects the recorder to its analyser, so the take is what the listener hears,
  pitch, speed, key lock, loops and compare included. Never on DRM (`mediaKeys`: the chain is silent there anyway) and
  never under an ad: `startRecording` refuses on `drm-silent`, and an ad, a pause or a seek **holds** the take.
- **Holds, not silence.** `hold()` / `resume()` take the context's frame counter on the main thread; the held interval
  is cut out of the chunks frame-accurately when they arrive. A mark made inside a hold lands on the cut. The video
  paused for a minute gives a take with no minute of silence in it.
- **Every move logged at the audio clock.** `start`, `params` (only when they changed), `loop` (latch / release),
  `seek`, `hold`, `resume`, `stop`, each with its take frame. Params, loops and seeks also become WAV cue points with
  labels (`pitch +2 st · 0.94×`, `loop 4 beats`, `seek 12.50 s`), so Audacity, Logic, Reaper and ffmpeg show them.
- **Nothing lost, nothing invented.** Chunks are 4096 frames, stamped with the context frame of their first sample and
  posted as transferables; a gap in the stamps is counted as `dropped`, never written as silence. Stop waits for the
  worklet's `flushed` answer so the last partial chunk is in the file (1.5 s timeout for a dead port). The node is
  armed through `processorOptions`, not a message, so it records from its first render quantum.
- **The file.** RIFF/WAVE, PCM tag 1, 24 bit (16 available), `cue ` + `LIST/adtl/labl`, pad byte on odd lengths.
  Samples are `round(x × 2²³)` clipped, NaN → 0. The writer refuses to pass the RIFF 4 GB limit; the recorder caps a
  take at an hour (1.04 GB at 48 kHz). Two files per take: `<name>.wav` and `<name>.moves.json`, named
  `kari-YYYY-MM-DD-HH-MM-<title>-+2st-0.94x`, handed to the browser's downloads through an anchor (no `downloads`
  permission).

**Compiled out of the public build.** `scripts/build.mjs` defines `__KARI_RECORD__`; the committed `extension/`
and every GitHub release and store zip are the public build, with no `kari-recorder` processor, no WAV writer and no
`__kari.record` in the bundles (a test diffs the committed bundles for those strings). `KARI_RECORD=1 npm run build`
(or `KARI_RECORD=1 npm run zip`) compiles the take in and marks the build stamp `+rec`; that zip is for Jesse's Mac,
never for the store, until the ruling.

Files: `src/shared/wav.ts` (writer), `src/worklet/recorder.js` (the pure stage), `KariRecorder` in
`src/worklet/processor.js`, `src/content/audio/recorder.ts` (the take), `startRecording` / `stopRecording` and the
hold / mark calls in `src/content/audio/controller.ts`, `recording` / `recFrames` on `AudioStatus` and the SoundCloud
`HookStatus`.

## Prior art read

- **YT Clip Recorder** (MIT, GitHub): an AudioWorklet that posts Float32 chunks to an offscreen page which writes a
  WAV. Confirmed the shape (worklet → chunks → writer) and that an outputs:0 worklet node still runs. Its README says
  the Chrome Web Store did not accept it: a YouTube audio saver installs by hand. Code here is written fresh.
- **Google's AudioWorklet samples**: the port protocol and transferables.
- Store-listed pitch tools (Transpose, Note by Note, Slowed+Reverb, Lento) all say they do not save audio; see the
  feature doc for the legal section.

## Checks run (2026-11-03)

Every check reads the bytes through a path the writer did not produce.

- `tests/wav.test.mjs` (17): a RIFF reader written from the spec walks every chunk and decodes the samples; codes for
  0, ±1, half, clipping, rounding and NaN; round trip within 2⁻²⁴; mono → stereo; streaming == one-shot byte for
  byte; odd-length pad; cue order, ids, labels, 64-byte clip on a character boundary; the cue table limit; the RIFF
  cap; then **Python's `wave` module** and **ffprobe** read a file back (`pcm_s24le`, 48 kHz, 2 ch, 1.000 s).
- `tests/recorder.test.mjs` (9): the pure stage (chunking, flush on stop, frame stamps, silence for an inactive
  source, mono repeat); the **shipped** `extension/worklet.js` registering `kari-recorder`, fed 5000 frames and
  reassembled bit for bit from its chunks, `flushed` on stop, `close` ends it; the main-thread `Recorder` with a fake
  node driven by the real stage: a hold cut frame-accurately (a 24-bit-exact ramp names every frame), moves and cues
  on the right frames, a lost chunk counted not silenced, the dead-port timeout, the hour cap, an empty take.
- `tools/probe/record.mjs` (19/19 rows): real Chromium. **Offline** 48 kHz stereo, a ramp left and a sine right,
  suspended at 0.25 s (hold), 0.45 s (resume) and 0.9 s (stop): the take holds exactly 33 664 frames (43 264 − 9 600),
  **Chrome's own `decodeAudioData`** matches the rendered buffer with the hold cut, left channel exact, right
  ≤ 5.96 × 10⁻⁸ (one 24-bit half-step), 0 dropped, stop answered in 5 ms while the context was suspended, moves and
  cues on the cut. **Realtime** `AudioContext`, an oscillator for one second: 48 128 frames against a 48 512-frame
  clock, 0 dropped, peak 0.5000 (the gain), stop answered in 7 ms. **Download path**: `downloadTake` lands
  `…ramp-take-+2st-0.94x.wav` (202 160 B, byte count exact) and `….moves.json`; ffprobe and Python read the saved file.
- `npm test`: 107 pass. `npx tsc --noEmit` clean. `extension/` rebuilt and committed (CI diffs it).

The probe caught one real bug before any ear did: the first version armed the recorder with a `rec on` message, and
an offline context rendered 12 032 frames before the port delivered it (the take began at the hold). Arming through
`processorOptions` fixed it; the realtime run had hidden it (a few milliseconds of lost head).

## UNVERIFIED

- Not heard: no take has been played back by a person. The decoder comparison says the samples are right; an ear
  check on a real YouTube page is the release thread's.
- Not run on a live YouTube page or in the SoundCloud MAIN world: the controller wiring (`startRecording` through the
  ad / pause / seek holds) is typed and built, the recorder underneath is probed; the end-to-end on youtube.com waits
  for the button slice and a signed-in Chrome.
- Memory of a long take: chunks are written to `Uint8Array` parts in the page; an hour at 48 kHz is 1.04 GB in the
  tab. Fine for a take of minutes; storage in IndexedDB via an offscreen page is the next slice.

## Ruling, 08:57 UTC the same day: it ships in the store build

Jesse: "skip the local build, I want to push to Google Chrome and download from there." The challenge was made once
(Chrome Web Store policy bans extensions that enable download of copyrighted media; review can reject or pull Kari,
and the strike lands on the Cantum publisher account) and his ruling stands. So `scripts/build.mjs` now defaults
`__KARI_RECORD__` on, the committed `extension/` carries the recorder and the pill, the bundle test asserts their
presence, `KARI_RECORD=0 npm run build` is the build without them (stamp `+norec`), `docs/PRIVACY.md` says what a
take is and where it goes, and the store listing names the button. No new permission: the files go through an anchor
to the browser's Downloads.
